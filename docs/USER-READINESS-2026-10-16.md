## 需要优先修复的功能问题

### UR-01 · P1：设置页会用过期模型覆盖侧栏选择

**复现：** 打开一次连接设置，关闭后从侧栏切换模型，再打开连接设置。顶部状态取当前配置，模型输入框却仍取第一次创建的草稿；随后保存连接设置会提交这个旧模型。

**实际证据：** 原生样本中当前配置已为 `audit-other-model`，重新显示的模型输入框仍为 `deepseek-flash`。

**原因：** [settings.js](../src/ui/settings.js) 第 66 行用 `connectionDraft ||=` 初始化，`hide()` 只清理计时器，没有协调外部配置变化；提交时把完整草稿交给 `configureConnection()`。

**验收要求：** 未修改的字段跟随当前配置；有未保存修改时明确保留、丢弃或解决冲突。再次打开设置、从侧栏换模型、应用设置三者必须保持一致，保存其他字段不得悄悄切回旧模型。

### UR-02 · P1：附加选区同时附加整篇笔记

**复现：** 选中笔记的一小段，使用“附加当前笔记或选区”。界面显示“已附加选区”，但模型上下文还包含该笔记全文。

**实际证据：** 用 `SELECTED` 和 `UNSELECTED_PRIVATE_SAMPLE` 构造独立笔记样本，执行生产代码的 `attachActive()` 和 `contextFor()` 后，选区为前者，`notes` 仍包含后者。本测试没有发出网络请求；正常发送时该上下文会进入请求。

**原因：** [plugin.js](../src/plugin.js) 第 474 行无条件加入 `mentions`，第 511 行随后读取全文；[chat-view.js](../src/ui/chat-view.js) 第 342 行的菜单名称没有表达“选区加全文”。

**影响：** 用户无法通过选择一小段明确控制引用范围，可能发送超出预期的内容，并使长笔记更容易超过上下文大小限制。

**验收要求：** 分开“仅选区”和“整篇笔记”，引用标签可预览真实内容和范围；仅选区测试应证明未选中内容不在请求中。若保留全文行为，必须在发送前明确展示。

### UR-03 · P1：Skill 路径显示值与实际保存值不一致

**复现：** 原路径为 A，在 Skills 页输入 B，切换到资料页再返回 Skills。输入框显示 A，此时点击保存，实际保存 B。

**实际证据：** 原生内存样本返回 `shown: C:/audit-old`、`saved: C:/audit-new`。

**原因：** [workspace-panel.js](../src/ui/workspace-panel.js) 第 163 行渲染已保存值，但第 171 行提交优先使用未展示的 `skillDraft`。

**验收要求：** 显示、校验和提交使用同一个草稿；切换页签保留可见草稿；保存成功或明确取消后再重置。不能保存用户当前看不到的路径。

## 首次使用与发布缺口

### UR-04 · P1：新设备缺少可完成的安装引导

连接设置要求用户填写 OpenCode 可执行文件，运行时又严格限定 1.19.0。自动检测只寻找已安装文件；找不到时没有直接提供对应版本的安装步骤、下载入口或后续诊断。现有 README 主要说明配置和原位更新，不能完整引导一位只有 Obsidian 和 API Key 的用户完成首次使用。

[setup-diagnostics.js](../src/backend/setup-diagnostics.js) 的 Windows 检测覆盖专用安装位置和 PATH 下的 `opencode.exe`，未覆盖常见 npm shim 对应的嵌套安装路径。这一子项是代码覆盖缺口，未在干净机器实装复现，不能算作所有 npm 安装均失败。

**验收要求：** 在没有现成 OpenCode 和凭据的 Windows 环境，按公开说明独立完成安装、版本检查、供应商配置和首条回复。明确提供 1.19.0 的受支持安装方式，不让用户误装任意最新版。OpenCode 官方目前提供多种安装方式并区分 V1/V2，因此必须固定本插件的兼容路径，而不是只链接通用首页。[官方安装说明](https://opencode.ai/docs/)

### UR-05 · P2：重启后的凭据使用流程不完整

“API Key（仅本次运行）”确实不会持久化；这是当前设计，不是保存功能失效。但新用户只在插件中输入 Key 后，下次启动仍需重新输入，除非另外在 OpenCode 配置凭据。界面只显示是否检测到凭据，没有引导完成长期配置。

**验收要求：** 明确提供临时使用与长期配置两条路径；长期路径应有具体操作、成功反馈和重启验收。避免把 Key 写入公开源码或普通诊断日志。连接本地服务成功与供应商鉴权成功应继续分开显示。

### UR-09 · 发布门槛：分支已推送，发行渠道尚未准备好

本次查询结果：候选分支已在远端；默认分支 `main` 的 manifest 仍为 0.2.1；GitHub Release 列表为空；Actions workflow 数为 0。

**正式发行前还需完成：**

1. 解决本报告的 P1 项目，确认候选代码合入哪个发布分支。
2. 从干净检出自动执行构建与回归，校验版本和三个发行文件。CI 是可重复交付措施，不是声称官方要求必须使用 GitHub Actions。
3. 按确定版本建立 tag 和 Release，附上 `main.js`、`manifest.json`、`styles.css`、更新说明及兼容范围。
4. 测试首次安装、旧插件 ID 原位更新、禁用再启用、重启，以及更新失败时恢复旧插件文件。
5. 补真实 DeepSeek 的最小对话、工具调用、鉴权失败、断网/超时和停止任务验收；本次未重新执行付费远程推理，不能由“本地连接正常”推断这些项目通过。
6. 若目标是 Obsidian 社区插件目录，再走官方提交与审核流程；本报告没有核实该插件是否已提交目录，不能把 GitHub 分支推送视为社区上架。

Obsidian 从与 manifest 版本匹配的 GitHub Release 下载插件文件，因此源码推送本身不完成发行。[官方发布流程](https://docs.obsidian.md/Plugins/Releasing/Submit%20your%20plugin)

## 功能细节与外观

### UR-06 · P2：资料目录的未提交输入随页签切换丢失

在资料页输入目录但尚未添加，切到 Skills 再回来，目录输入变为空。原生样本已复现。[workspace-panel.js](../src/ui/workspace-panel.js) 每次渲染重新创建空输入框。

**验收要求：** 保存目录草稿直到添加成功、用户明确清除或关闭面板；目录选择器返回的路径也遵守同一规则。

### UR-07 · P2：主侧栏已基本统一，弹窗的表单布局仍不统一

实际截图中，主侧栏的标题、图标、消息气泡、底部输入区和更多菜单分组基本一致；340 px 侧栏在明暗主题下没有横向溢出。原生样本正文中的表格与代码块正常显示。当前问题主要集中在辅助面板：

- Skills 路径输入框被说明文字挤成很窄的一格，不适合 Windows 长路径。
- 模型搜索框只占弹窗一小段宽度，对话搜索框却铺满整行；资料路径框的高度和边框观感又不同。
- 资料页两个相邻按钮及工作目录页的两个历史按钮缺少一致间距和主次层级。
- 连接页的四个阶段、说明文字和大块设置行使 API Key 与应用按钮落在首屏之外。切页签后滚动能回到顶部，本次没有复现滚动位置残留错误。
- 短对话历史列表将标题居中、日期靠右，浏览多条记录时不如统一左对齐标题和次级时间容易扫读。

**验收要求：** 统一输入高度、圆角、焦点样式、按钮间距和操作区；路径与搜索独占完整行；首次连接以必要字段为主，把高级字段折叠。用长路径、长模型名、20 条历史记录及缩放状态重新验收。中文字体来自宿主字体设置，本报告不把用户主题字体直接归为插件缺陷。

相对于用户期待的 Codex 式侧栏，主对话入口已经接近；历史会话仍需打开弹窗，模型也通过弹窗选择。是否改成侧栏内切换属于产品取舍，不是当前实现失效，但值得在视觉改版时统一决定。

### UR-08 · P2：交互卡片运行入口缺少就地权限说明

设置和文档已说明 DataviewJS 不受普通工具权限约束，但卡片上的“运行”按钮旁仅显示运行状态。[chat-view.js](../src/ui/chat-view.js) 第 1133 行直接调用 Dataview 的 `executeJs()`。

**验收要求：** 首次运行处明确说明代码由 DataviewJS 执行、具备宿主权限，并提供代码预览。继续保持用户主动运行；工具权限预设不能被误读为卡片的执行沙箱。
